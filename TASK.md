# ТЗ: Concurrent Task Processing Service

## 1. Идея проекта

Сервис, который принимает задачи (URL для проверки, "тяжёлые" вычисления, эмуляция I/O) через HTTP API, распределяет их между пулом воркеров, обрабатывает конкурентно с учётом приоритетов и лимитов, кэширует результаты и корректно завершает работу по сигналу ОС, не потеряв ни одной задачи "в полёте".

Название рабочее: **TaskRunner**.

Проект специально спроектирован так, чтобы каждая тема из списка была не факультативной, а обязательной для корректной работы системы.

---

## 2. Архитектура (модули)

```
cmd/taskrunner/main.go       — точка входа, graceful shutdown
internal/api/                — HTTP-слой (net/http)
internal/scheduler/          — очередь задач, приоритеты, select
internal/worker/             — пул воркеров, goroutines, context
internal/cache/              — потокобезопасный кэш результатов
internal/limiter/            — rate limiter / семафор
internal/metrics/            — атомарные счётчики
internal/pubsub/             — fan-out уведомлений о результатах
internal/config/             — конфиг + sync.Once для singleton-ресурсов
```

---

## 3. Функциональные требования по модулям

### 3.1. HTTP API (`internal/api`)
- `POST /tasks` — принять задачу (URL для проверки доступности + приоритет `low`/`high`), вернуть `task_id`.
- `GET /tasks/{id}` — получить статус/результат из кэша.
- `GET /metrics` — текущие счётчики (обработано, в очереди, ошибок, среднее время).
- `POST /shutdown` (опционально) — инициировать graceful shutdown вручную, для тестов.

**Требование:** каждый входящий HTTP-запрос порождает `context.Context` с таймаутом (например, 5 сек на постановку в очередь), который прокидывается дальше по всей цепочке обработки задачи.

### 3.2. Планировщик (`internal/scheduler`)
- Два канала: `highPriorityCh chan Task` и `lowPriorityCh chan Task` (буферизованные, размер задаётся конфигом).
- Диспетчер, который через `select` вычитывает сначала high, потом low (с проверкой обоих через `select` с `default`, чтобы не голодал low).
- Если оба канала полны — либо блокировка с ожиданием (backpressure), либо отказ (`503`) — сделать оба режима переключаемыми флагом, чтобы явно прочувствовать разницу.

### 3.3. Пул воркеров (`internal/worker`)
- N воркеров (N — из конфига), каждый — отдельная горутина, слушающая оба канала планировщика через `select`.
- Каждый воркер также слушает `ctx.Done()` в том же `select` — это ключевое место для отработки cancellation.
- Обработка задачи = "тяжёлая операция" (реальный HTTP-запрос к проверяемому URL с `http.Client{Timeout: ...}`, либо `time.Sleep` для симуляции — сделать оба варианта, переключаемые флагом).
- **Ограничение параллелизма** внутри воркер-пула — через семафор на буферизованном канале (`chan struct{}` ёмкостью M), даже если воркеров больше — так вы прочувствуете разницу между "количество горутин" и "количество одновременных операций".

### 3.4. Кэш результатов (`internal/cache`)
- `map[string]TaskResult`, защищённая `sync.RWMutex`.
- Чтение (`GET /tasks/{id}`) — через `RLock`.
- Запись результата воркером — через `Lock`.
- **Дополнительно:** реализовать вторую версию кэша на `sync.Map` и написать бенчмарк (`go test -bench`), сравнивающий `RWMutex`-версию и `sync.Map` при разных пропорциях читателей/писателей. Это даст практическое понимание, когда что уместно.

### 3.5. Rate limiter (`internal/limiter`)
- Ограничение количества исходящих проверок URL в секунду (например, не более 10/сек к внешним хостам).
- Реализовать вручную через `time.Ticker` + канал токенов (без `golang.org/x/time/rate`, чтобы разобраться руками).
- Токен-бакет: горутина-пополнитель кладёт токен в канал по тикеру; воркер, прежде чем сделать запрос, забирает токен через `select` с таймаутом (если токена нет N мс — вернуть "перегружено").

### 3.6. Метрики (`internal/metrics`)
- Счётчики: обработано успешно, обработано с ошибкой, текущее число активных воркеров, суммарное время обработки.
- Реализовать через `atomic.Int64` / `atomic.Uint64` (пакет `sync/atomic`, новый typed API), **без мьютексов** — чтобы явно увидеть разницу в подходах.
- `GET /metrics` формирует снапшот атомарным чтением всех полей.

### 3.7. Pub/Sub уведомления (`internal/pubsub`)
- Подписчики (например, WebSocket-клиенты или просто горутины-логгеры) подписываются на канал результатов.
- Реализовать fan-out: один канал результатов от воркеров → broadcaster-горутина → рассылка в N персональных каналов подписчиков через `select` с `default` (чтобы медленный подписчик не блокировал остальных — "неблокирующая отправка").
- Использовать `sync.Once` для ленивой инициализации broadcaster-горутины при первом подписчике.
- Использовать `sync.WaitGroup` для ожидания завершения всех подписчиков при остановке.

### 3.8. Конфигурация (`internal/config`)
- Singleton конфиг, инициализируемый один раз через `sync.Once`, даже если `LoadConfig()` вызывается из нескольких горутин параллельно (написать тест, который это проверяет через `go test -race`).

## 4. Graceful Shutdown (ключевое требование ко всему проекту)

`main.go` должен:

1. Слушать `os.Signal` (`SIGINT`, `SIGTERM`) через `signal.NotifyContext`.
2. При получении сигнала:
   - Перестать принимать новые HTTP-запросы (`http.Server.Shutdown(ctx)` с отдельным таймаутом, например 10 сек).
   - Закрыть входные каналы планировщика (`close(highPriorityCh)`, `close(lowPriorityCh)`), дав воркерам дочитать то, что уже в канале.
   - Дождаться завершения всех воркеров через `sync.WaitGroup.Wait()`, но **не бесконечно** — обернуть ожидание в `select` с `context.WithTimeout` (например, 15 сек), и если не успели — залогировать принудительное прерывание.
   - Остановить rate-limiter (закрыть канал токенов / отменить его контекст).
   - Дождаться broadcaster'а pub/sub.
   - Только после этого — `os.Exit(0)`.
3. **Важно:** ни одна задача, уже принятая в канал, не должна быть потеряна молча — либо обработана, либо залогирована как "отменена при shutdown".

Это заставит явно продумать порядок закрытия: HTTP → очередь → воркеры → вспомогательные горутины, и понять, почему порядок важен (закрыть канал раньше времени = паника "send on closed channel").

## 5. Матрица "тема → где используется"

| Тема | Где обязательно встречается |
|---|---|
| Горутины | воркер-пул, broadcaster, пополнитель токенов, HTTP-сервер |
| `context.Context` | таймаут на HTTP-запрос, отмена задачи, `signal.NotifyContext` для shutdown, таймаут на ожидание токена |
| `sync.Mutex` / `RWMutex` | кэш результатов |
| `sync.Once` | конфиг, ленивая инициализация broadcaster |
| `sync.WaitGroup` | ожидание воркеров и подписчиков при shutdown |
| `sync/atomic` | метрики |
| `sync.Map` | альтернативная реализация кэша (для сравнения) |
| Каналы (буферизованные/небуферизованные) | очереди приоритетов, семафор, токен-бакет, fan-out |
| `select` | диспетчер приоритетов, воркер (задача vs cancel), неблокирующая отправка подписчикам, ожидание токена с таймаутом |
| Graceful shutdown | `main.go`, весь п.4 |

## 6. Нефункциональные требования

- Весь код должен проходить `go test -race` без предупреждений — это единственный способ доказать себе, что блокировки расставлены верно.
- Обязательные unit-тесты:
  - Конкурентная запись/чтение кэша (проверка гонок).
  - Тест, что при отмене родительского контекста задача в воркере действительно прерывается (не "успевает" завершиться).
  - Тест graceful shutdown: отправить N задач, сразу инициировать shutdown, убедиться, что все N обработаны или явно помечены отменёнными, и нет паник.
  - Тест rate limiter: за T секунд не более `T * rate` запросов ушло реально.
- Логирование через `log/slog` с указанием goroutine-контекста (можно просто добавлять `task_id` в атрибуты).
- Нагрузочный тест / bench на 1000+ одновременных задач.

## 7. Этапы разработки (рекомендуемый порядок)

1. Каркас: конфиг + `sync.Once`, HTTP-сервер без логики.
2. Кэш на `RWMutex` + тесты гонок.
3. Планировщик с двумя каналами + `select`-диспетчер.
4. Пул воркеров, слушающих `ctx.Done()` через `select`.
5. Семафор-ограничитель параллелизма внутри пула.
6. Rate limiter на токен-бакете.
7. Метрики на atomic.
8. Pub/sub fan-out с неблокирующей отправкой.
9. Graceful shutdown — собрать всё воедино, самый сложный и самый ценный этап.
10. Сравнительный бенчмарк `RWMutex` vs `sync.Map`.
11. Нагрузочное тестирование + `-race`.

## 8. Критерии приёмки

- [ ] `go build ./...` и `go vet ./...` без ошибок.
- [ ] `go test ./... -race` проходит.
- [ ] При `kill -SIGTERM <pid>` во время нагрузки сервис завершает работу без паник и без "зависших" горутин (проверить через `pprof`/`goroutine leak detector`, например `go.uber.org/goleak`).
- [ ] Отправка задачи с уже истёкшим контекстом (`context.WithTimeout(ctx, -1)`) корректно возвращает ошибку, а не зависает.
- [ ] Бенчмарк `RWMutex` vs `sync.Map` даёт результат и написан вывод (2-3 предложения), в каком случае что выгоднее.

## 9. Возможные усложнения (по желанию, если основа усвоена легко)

- Приоритетная очередь не из 2, а из N уровней приоритета через `container/heap` + один диспетчер-канал.
- Circuit breaker вокруг исходящих HTTP-запросов (ещё один повод для `atomic` + таймеров).
- Персистентность очереди (чтобы при рестарте не терять задачи) — потребует переосмыслить, что значит "graceful" в этом контексте.
- Distributed rate limiting через Redis (если хочется выйти за рамки одного процесса).

## 10. Что вы должны уметь объяснить себе после проекта

Хороший тест на понимание — после реализации попробовать вслух ответить:

1. Почему нельзя просто `close()` канал, в который ещё могут писать несколько горутин?
2. Чем `select` с `default` отличается от `select` без него с точки зрения блокировки?
3. Когда `RWMutex` медленнее обычного `Mutex`?
4. Почему `context.WithTimeout` — это не "таймер", а именно сигнал отмены, который нужно явно проверять?
5. Что произойдёт, если забыть `defer wg.Done()` в одном из воркеров?
6. Почему race detector не находит вообще все гонки?

Если на все шесть можете ответить без подглядывания в код — тема усвоена.
