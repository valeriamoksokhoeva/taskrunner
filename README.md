# TaskRunner — конкурентная обработка задач на Go

Сервис принимает задачи через HTTP, раскладывает их по двум очередям с разным
приоритетом, обрабатывает пулом воркеров и корректно завершается по сигналу ОС,
не теряя того, что уже принято в работу.

Зависимостей вне стандартной библиотеки нет (кроме `goleak` в тестах).

## Запуск

```bash
go run ./cmd/taskrunner
```

Или в контейнере:

```bash
docker build -t taskrunner .
docker run --rm -p 8080:8080 taskrunner
```

Сервис слушает `:8080`.

| Параметр | По умолчанию | Что задаёт |
|---|---|---|
| `-workers` | 8 | число горутин-воркеров |
| `-concurrency` | 4 | сколько операций выполняется одновременно (семафор) |
| `-queue-size` | 100 | размер буфера каждой из двух очередей |
| `-rate` | 10 | лимит исходящих запросов в секунду |
| `-overflow` | `reject` | поведение при полной очереди: `reject` (503) или `block` |
| `-mode` | `http` | `http` — реальная проверка URL, `sleep` — симуляция нагрузки |

Конфиг загружается один раз через `sync.Once`, даже если `LoadConfig()`
вызывается параллельно из нескольких горутин.

## API

| Метод | Путь | Описание |
|---|---|---|
| POST | `/tasks` | принять задачу, вернуть `task_id` |
| GET | `/tasks/{id}` | статус и результат задачи |
| GET | `/metrics` | снапшот счётчиков |

```bash
# поставить задачу
curl -X POST localhost:8080/tasks \
  -d '{"url":"https://example.com","priority":"high"}'
# {"task_id":"..."}

# забрать результат
curl localhost:8080/tasks/<task_id>

# счётчики
curl localhost:8080/metrics
```

Каждый входящий запрос порождает `context.Context` с таймаутом на постановку в
очередь. Этот контекст прокидывается дальше по всей цепочке — до отмены задачи
внутри воркера.

## Как устроено

```
cmd/taskrunner/main.go   — точка входа, порядок остановки
internal/api/            — HTTP-слой
internal/scheduler/      — две очереди, select-диспетчер
internal/worker/         — пул воркеров, семафор
internal/cache/          — результаты: RWMutex-версия и sync.Map-версия
internal/limiter/        — токен-бакет
internal/metrics/        — счётчики на sync/atomic
internal/config/         — конфиг через sync.Once
```

### Приоритеты без голодания

Две буферизованные очереди — `high` и `low`. Диспетчер сначала пробует прочитать
из `high` через `select` с `default`, и только если там пусто, идёт в `low`.
`default` здесь принципиален: без него `select` заблокируется на пустой
высокоприоритетной очереди и низкий приоритет не получит шанса вообще.

При переполнении обеих очередей поведение переключается флагом: либо отказ с
`503`, либо backpressure — вызывающая сторона ждёт места. Это два разных
контракта с клиентом, и выбор между ними сделан явным, а не спрятан в коде.

### Горутины и одновременность — не одно и то же

Воркеров N, но одновременно выполняющихся операций не больше M: перед работой
воркер берёт место в семафоре на буферизованном канале `chan struct{}` ёмкостью
M. Это позволяет держать много дешёвых горутин, ожидающих задачи, и при этом
ограничивать нагрузку на внешние сервисы.

### Rate limiter

Токен-бакет написан руками, без `golang.org/x/time/rate`: горутина-пополнитель
по `time.Ticker` кладёт токены в канал, воркер забирает токен через `select` с
таймаутом. Если токена нет за отведённое время — задача помечается как
«перегружено», а не ждёт бесконечно.

### Отмена

Воркер в одном `select` слушает и очередь, и `ctx.Done()`. Контекст — это не
таймер: он не прерывает работу сам, его сигнал нужно явно проверять, поэтому
длинные операции разбиты так, чтобы между ними была точка проверки отмены.

### Метрики

Счётчики обработанных, ошибочных и активных задач — на `atomic.Int64`, без
мьютексов. `GET /metrics` собирает снапшот атомарным чтением полей.

### Graceful shutdown

`signal.NotifyContext` ловит `SIGINT` и `SIGTERM`, дальше остановка идёт строго
по порядку:

1. `http.Server.Shutdown(ctx)` — перестаём принимать новые запросы.
2. Закрываем очереди — воркеры дочитывают то, что уже в буфере. Закрыть их
   раньше шага 1 нельзя: обработчик, уже находящийся в процессе записи, получит
   панику «send on closed channel».
3. Ждём воркеров через `WaitGroup`, но не бесконечно — ожидание обёрнуто в
   `select` с `context.WithTimeout`. Если не уложились, пишем в лог
   принудительное прерывание.
4. Останавливаем rate limiter.

Гарантия: задача, принятая в очередь, либо обработана, либо залогирована как
отменённая при остановке. Молча не теряется ничего.

## Кэш: RWMutex vs sync.Map

Кэш результатов реализован дважды — на `map` под `sync.RWMutex` и на `sync.Map` —
и сравнён бенчмарком при разных пропорциях читателей и писателей:

```bash
go test ./internal/cache -bench=. -benchmem
```
